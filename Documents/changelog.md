## 2026-08-21 — Full-project assessment + fixes: government contract rounding bug, stockpile race, realtime guard bypasses, SSOT cleanup, dead code, API route sweep

A full assessment pass (three parallel audits: SSOT/duplication, money-path correctness, frontend/state + utility patterns), followed by fixing everything found. No live-database verification was possible this session (Docker unavailable, same limitation noted on several CityPlan sessions) -- all SQL changes were hand-reviewed carefully, not exercised against a local reset.

**Real bug found and fixed, migration [`119`](../supabase/migrations/20260819230000_119_government_contract_award_and_delivery.sql):** `deliver_government_contract_atomic` took a `numeric` `p_quantity` and wrote it straight into `business_inventory.quantity` (an `integer` column) with no rounding -- silent, since Postgres implicitly casts on assignment. Because `government_contracts.quantity_requested`/`quantity_delivered` are numeric (auto-generated replenishment contracts derive them from `population_baseline`-scaled math, essentially always fractional), a normal delivery would silently round the physical inventory count away from what was actually paid for and relieved, while cash/COGS stayed exact to the fraction -- a permanent, compounding books-vs-inventory mismatch. Confirmed the same migration already rounds the parallel `business_financial_events.quantity` field a few lines later; only the authoritative inventory write was missed. Fixed by flooring the deliverable amount to whole units up front (capped against `ceil(v_remaining)`, not `v_remaining` itself, so a fractional remainder under 1 unit can still be closed out with one final whole unit instead of getting stuck forever), plus an explicit `round(...)::integer` on the actual write as defense in depth. Also added `.int()` to `deliverGovernmentContractSchema` (`src/domains/government/validations.ts`) so the API boundary rejects fractional quantities too.

**Real race condition found and fixed, migration [`114`](../supabase/migrations/20260819180000_114_city_stockpiles.sql):** `_materialize_city_stockpile_ids`'s single `UPDATE ... FROM` relied on the update's own row lock, per its original comment -- correct for one caller, not for three (the 5-minute due sweep, the daily government pass, and `deliver_government_contract_atomic`, which calls it twice on the same row in one transaction). A blocked UPDATE's EvalPlanQual re-check on lock conflict only re-verifies join/WHERE quals, not the already-computed SET expressions, so a second writer could silently overwrite a first writer's correctly-depleted stock with stale-computed values. Fixed by explicitly locking every target row (`order by id`, to avoid a lock-order deadlock between overlapping calls) in its own statement before the CTE-based UPDATE runs, so the UPDATE executes as a fresh statement against fresh (post-lock) data under READ COMMITTED's per-statement snapshot semantics.

**Non-strict custom aggregate, migration [`112`](../supabase/migrations/20260819160000_112_world_city_economic_state.sql):** `product_agg`'s transition function had no `STRICT` modifier, so an event's `modifiers` JSON with an explicit `null` for a matching key would poison the whole running product to `null`, silently resetting that index to neutral via the outer `coalesce`. Added `strict` -- Postgres now skips the transition entirely on a null input instead, leaving every other event's real contribution untouched. Dormant today (no events seeded yet), but would have misbehaved silently the first time admin/scenario event content used a malformed modifier.

**Two recurrences of the 2026-08-15 stale-UI race**, found by re-auditing every direct-fetch call site against `runGuardedSliceFetch`: `BusinessesClient.tsx`'s `handleSelectBusiness` fetched and applied its detail slice via a local `selectRequestRef` token only, never the shared per-business guard key `realtime-provider.tsx`'s own refresh uses for the same slice -- fixed by routing through `runGuardedSliceFetch` and switching the panel to read the business detail reactively from the store (`useGameStore` selector) instead of a disconnected local `useState` copy, so it also now picks up live realtime patches, which it never did before. `useBusinessDetailsController.ts`'s `refreshFinanceDashboard` (period-switch on `/businesses/[id]`) had the same bypass -- fixed with its own dedicated guard key (`${businessDetail(businessId)}:finance`, not the shared full-detail key, since sharing it would let a period switch silently piggyback on an in-flight realtime refresh and never actually fetch the newly requested period).

**SSOT cleanup:** `tick-manufacturing`'s bare local `XP_PER_LEVEL = 100` is now `MANUFACTURING_XP_PER_LEVEL` in `shared/production/manufacturing.ts`, matching `tick-extraction`'s existing `EXTRACTION_XP_PER_LEVEL` pattern. Fixed 4 imports (`market/service.ts`, `production/service.ts`, `upgrades/{runtime,projects}.ts`) reaching past the `@/domains/businesses` barrel into `/service`/`/types` directly, per `AI_GUIDE.md`'s own cross-domain import rule. Confirmed one previously-flagged duplication is actually already resolved: `supabase/functions/_shared/business-upgrades.ts` no longer hand-duplicates upgrade effects for a subset of keys -- it imports `resolveBusinessUpgradeEffects` from `shared/upgrades/effects.ts` directly, covering all ~105 keys exhaustively (see this file's correction note on the 2026-08-18 entry below).

**Dead code removed:** `resolveMultiplier`/`resolveReductionMultiplier` (`shared/upgrades/runtime.ts`) -- zero callers, and duplicated (with drift risk) by `effects.ts`'s `resolveUpgradeEffectValue`, which is the version actually used. `computeNextReorderAt` (`shared/cities/stockpiles.ts`) -- zero callers, not even from its own sibling `projectCurrentStock`. **Deliberately left alone**, despite also having zero callers: `calculateHourlyWage` (`shared/employees/payroll.ts`) and the entire `shared/cities/labor.ts` module -- both are documented, staged work for a future hiring-wage feature (see `AGENTS.md`), not accidental leftovers; wiring them in is an economy-design decision, not a cleanup.

**API route sweep:** `src/app/api/_shared/route-helpers.ts`'s `handleAuthedRequest`/`handleAuthedJsonRequest` existed and were proven in ~14 route files, but ~56 others still hand-rolled the equivalent auth-check/zod-parse/try-catch boilerplate. Converted all 56, preserving exact status codes, error messages/fallbacks, and success-path logic -- only the wrapper boilerplate changed. 6 routes deliberately left untouched: `auth/login`, `auth/logout`, `auth/register` (pre-session flows), `auth/me` (intentionally returns 200 with `user:null` when unauthenticated, not 401), `public-stats` (genuinely public), `realtime-auth` (its own distinct cookie/JWT flow). Net -1012 lines across the 56 files.

**New utility:** `src/hooks/use-async-action.ts` -- collapses the guard/reset/try-catch/finally shape repeated at mutation handlers across the authenticated `*Client.tsx` pages. Applied to `BankingClient.tsx`, which still had 5 separate `*Submitting` flags even after the 2026-08-15 fix unified their race-condition lock (`allBusy`) without touching the surrounding per-handler boilerplate itself.

**Docs:** removed 4 dead "read this first" pointers from `AI_GUIDE.md`/`AGENTS.md` (`Documents/Bugs.md`, `Notes.md`, `economy-audit-2026-03-09.md` no longer exist -- folded into this changelog once worked through), added `QualityEconomyPlan.md` as the current standing proposal in `AGENTS.md`'s read order, and moved `src/app/(authenticated)/contracts/ArchitecturalChange.md` (a fully-implemented store/realtime migration plan, misplaced in a random page folder with no connection to the contracts domain) to `Documents/Plans/Complete/RealtimeStoreMigration.md`.

Verified with a clean `npm run typecheck`, `npm run typecheck:edge`, and `npm run build` after every batch of changes. **Not verified against a live database this session** -- Docker unavailable; `npm run test:finance`/`test:db-security` could not be run against the migration 112/114/119 changes. Recommend a local `supabase db reset` + those two suites before this reaches hosted, given migrations 111-119 are still an open "not yet pushed" thread per `AGENTS.md`.

**Update, next session (2026-08-22), Docker available:** a clean `npx supabase db reset` applied all 119 migrations including the three edited above with no errors, and `npm run test:finance` (63 passed) / `npm run test:db-security` (12 passed) both passed clean. But a manual hand-check of the migration 119 fix against a deliberately fractional case (41.7 requested, delivering 42 whole units) caught a real bug **in the fix itself**: capping `v_to_deliver` against `ceil(v_remaining)` (to let a sub-unit remainder close out with one final unit) let `quantity_delivered` land above `quantity_requested` -- which `government_contracts`' own `quantity_delivered <= quantity_requested` CHECK (migration 117) forbids outright, so the RPC threw a constraint violation instead of the silent rounding bug it was meant to fix. Neither the existing automated test nor the earlier hand-review caught this, because the one delivery test in `test/finance/government-contract-delivery.test.ts` happens to use a `quantity_requested` that lands on a whole number by construction (`reorderPoint * 0.5` with round inputs), so it never exercised the fractional-cap path at all. **Corrected**: cap against `v_remaining` itself, not its ceiling -- `floor(least(p_quantity, v_remaining))` can never exceed `v_remaining`, so it can never violate the CHECK. The accepted tradeoff, confirmed by the same manual test: a sub-whole-unit remainder (e.g. 0.7 units) can never be fully closed by a real delivery, since a fractional physical delivery isn't possible either -- the contract just stays `in_progress` with that residual forever. Re-verified end to end by hand first (fresh `db reset`, manually inserting a fractional-remainder contract via `db query --local` and calling `deliver_government_contract_atomic` directly): delivering 42 against a 41.7 remainder now correctly delivers 41, leaves the contract `in_progress`, and `business_inventory.quantity` lands on a clean whole `59` (from 100), not a silently-rounded value. Then, per the lesson below, turned that manual check into a permanent test rather than leaving it as a one-off: added a new `describe` block to `test/finance/government-contract-delivery.test.ts` that constructs a deliberately fractional `quantity_requested` (41.7) directly instead of relying on the replenishment sweep (whose fixture always lands on a whole number), asserting the same three things the manual check did -- delivered=41, contract stays `in_progress`, inventory quantity is a whole `59` -- plus that a further 1-unit delivery attempt against the un-deliverable 0.7 residual correctly rejects rather than silently no-op'ing. `test:finance` now runs 64 tests (up from 63), both suites re-run clean (64 + 12 passed) after adding it. **Lesson, worth repeating from prior CityPlan sessions**: a fix to a rounding/edge-case bug needs its own edge-case test, not just "the existing suite still passes" -- the existing suite's silence here was a coincidence of its fixture data, not evidence the fix was correct.

## 2026-08-20 — CityPlan Phase 5: route-based abstract freight (player travel + shipping move off the region-tier system)

Per [`Documents/Plans/CityPlan.md`](Plans/CityPlan.md) ("Phase 5 - Route-Based Abstract Freight"), following Phase 4's government contracts. No new migration -- Phase 1's `city_routes` table (seeded, but reference-data-only until now) already had everything this phase needed; this was a pure application-layer change.

**Replaced the region-tier system, not just added an alternative.** `src/domains/cities-travel/topology.ts`'s `classifyTravelTier`/`getTravelTierDetails`/`TRAVEL_TIER_DETAILS` (four discrete distance bands: `same_region`/`adjacent_region`/`cross_country`/`far_cross_country`, each with a fixed minutes/cost regardless of the actual city pair) are gone. In their place, two pure formula functions take a `city_routes` row directly: `calculateRouteTravelMinutes` (`route.baseline_drive_minutes * LOGISTICS_TIME_SCALE`, per the plan's own formula) and `calculateRouteShippingQuote` (`max(minimumShipmentCharge, distanceMiles * chargeableWeightLb * baseRatePerLbMile) * world.transportCostIndex`, also per the plan). New [`src/config/logistics.ts`](../src/config/logistics.ts) holds the tuning constants the plan calls for keeping in config rather than schema: `LOGISTICS_TIME_SCALE = 1.0` (real-world driving pace -- `city_routes` was seeded at ~55mph in Phase 1, so e.g. New York City to Los Angeles is now a real ~50.7-hour route leg instead of the old tier system's flat 240 minutes), `TRAVEL_COST_PER_MILE`/`TRAVEL_MINIMUM_FARE` for player travel fares (not spelled out in the plan's own formulas, so picked to land in the same rough dollar range as the old tiers at comparable distances), and `DEFAULT_CHARGEABLE_WEIGHT_LB_PER_UNIT` -- a stand-in for the trucking reach goal's not-yet-built per-item `unit_weight_lb`, so `chargeableWeightLb` can be computed today without waiting on that schema; every `city_routes` row's `base_freight_cost_per_lb_mile` (seeded at a flat 0.015 in migration 111) is used as-is, unchanged.

**`calculateTravelQuote`/`calculateShippingQuote` moved from `topology.ts` to `service.ts` and became async**, since picking a route now means a real `city_routes` lookup (`getRouteBetweenCities`) plus `world_economic_state.transport_cost_index`, not a pure in-memory city-object comparison. `topology.ts` keeps the pure math (`calculateRouteTravelQuote`/`calculateRouteShippingQuote`, given a route + index, no DB); `service.ts` resolves the route/world state and delegates. All 4 call sites updated to `await` the new signatures: `src/app/api/travel/route.ts`, `src/app/api/travel/quote/route.ts`, `src/app/(authenticated)/travel/actions.ts` (both `getTravelQuoteAction`/`startTravelAction`), and `src/domains/inventory/service.ts`'s `resolveShippingPlan` (the function `transferItems`/`execute_inventory_transfer` calls to price and time every B2B/personal shipment, including the path a player uses to move goods into a government contract's destination city before `deliverGovernmentContract()` will accept them -- Phase 4's cross-city enforcement now gates on real route timing instead of the old tier estimate). `TravelQuote`/`ShippingQuote` (`types.ts`) dropped their `tier` field in favor of `distanceMiles`; the one UI consumer, `TravelClient.tsx`'s quote panel, now shows road distance instead of a tier label. The `TravelTier` type and its region-adjacency table (`ADJACENT_REGIONS`/`FAR_CROSS_COUNTRY_PAIRS`) are deleted outright, not deprecated -- nothing else referenced them (confirmed by a full-repo grep before removal).

**A real cross-runtime floating-point issue found and fixed in the test suite, not a regression in the RPC:** [`test/finance/shipping.test.ts`](../test/finance/shipping.test.ts) asserted `Number(destRows[0].total_cost) toBe (50 + shippingCost)` -- exact JS `===` on a float sum. Under the old tier system `shippingCost` was always a clean multiple of a per-unit rate (e.g. `10 * 0.25`); under route-based pricing it's a distance-derived value with less clean cents, and `50 + shippingCost` computed via raw JS double addition can differ from Postgres's exact `numeric` addition (echoed back and re-parsed) by less than a cent -- the classic `0.1 + 0.2` class of bug, just not usually visible at "nice" tier numbers. Fixed by rounding the expected value to the cent (`Math.round((50 + shippingCost) * 100) / 100`) before comparing, matching how money is rounded everywhere else in this codebase. Not a change to the domain code being tested, and not related to Phase 4's actual RPC/journal logic, which is unaffected.

**Manually sanity-checked against local Postgres** (not just unit-level): queried `city_routes`/`world_economic_state` directly and hand-computed both formulas for a short route (New York City-Chicago, 790 mi) and the longest seeded route (New York City-Los Angeles, 2790 mi) to confirm dollar figures land in a sane, non-absurd range before trusting the test suite's green result -- e.g. NYC-Chicago freight for 10 units comes to $11.85 ($1.185/unit), NYC-LA to $41.85 ($4.185/unit), both a similar order of magnitude to the old tier system's $0.05-$0.35/unit despite now varying continuously with real distance instead of jumping between 4 fixed bands.

Verified with a clean `npm run typecheck`, `npm run typecheck:edge` (no edge function touches this -- shipment dispatch/pricing happens in the Next.js API layer via `execute_inventory_transfer`, not a tick function; `tick-shipping` only finalizes due arrivals by wall-clock time and didn't need to change), `npm run build`, `npm run test:finance` (63 passed, 0 regressions once the float-precision assertion above was fixed), and `npm run test:db-security` (12 passed, unaffected -- no RPC/grant surface changed this phase).

**Deliberately out of scope for this pass** (per the plan's own phase breakdown): no City Page UI (the plan's proposed Logistics tab showing distance/time/freight estimates to other cities -- same "architecture ready, UI later" pattern every prior CityPlan phase has followed), no player-owned trucking (the reach goal; `chargeableWeightLb`'s `DEFAULT_CHARGEABLE_WEIGHT_LB_PER_UNIT` placeholder is exactly the seam the reach goal's real `unit_weight_lb` item metadata will plug into). Cross-city government contract enforcement itself was already built in Phase 4 (`deliver_government_contract_atomic`'s `wrong_city` rejection) -- this phase only changed how a player actually gets goods into the right city beforehand.

**Not yet pushed to hosted** -- this phase has no migration, so there's nothing new to `db push`, but it does change `src/app/api/travel/*`, `src/app/(authenticated)/travel/*`, and `src/domains/inventory/service.ts` behavior, none of which are deployed as edge functions; the Vercel/Next deploy carries this automatically whenever that next happens. Phases 1-4's migrations (111-119) remain the standing "not yet pushed to hosted" item -- see `AGENTS.md`'s open threads.

## 2026-08-19 — CityPlan Phase 4: government procurement contracts, plus a real Phase 3 bug fixed by finally running the migrations locally

Per [`Documents/Plans/CityPlan.md`](Plans/CityPlan.md) ("Phase 4 - Government Procurement Contracts"), following Phase 3's municipal stockpiles (below). Three migrations:

- **[`117`](../supabase/migrations/20260819210000_117_government_contract_providers_and_contracts.sql)** — new `government_contract_providers` (`provider_type` city|federal, `city_id` nullable with a CHECK tying it to `provider_type`, `provider_key` e.g. `city:boise`/`federal:us`, `display_name`, `is_active`, `metadata jsonb`) and `government_contracts` (`provider_id`, `city_id`, `stockpile_id`, `contract_type`, `item_key`, `quantity_requested`/`quantity_delivered`, `minimum_quality`, `unit_price`/`total_value`, `status` available→awarded→in_progress→fulfilled/closed plus expired/cancelled, `urgency`, `awarded_business_id`, `posted_at`/`deadline_at`/`closed_at`). Seeded one provider per active city plus a single static Federal placeholder (`federal:us`, `city_id null`). The idempotency guard the plan calls for ("`!equivalentActiveContract`", safe under concurrent workers) is a partial unique index on `government_contracts(stockpile_id) where status in ('available','awarded','in_progress')` rather than an application-side check -- a stockpile can have at most one live contract at a time, structurally.
- **[`118`](../supabase/migrations/20260819220000_118_government_replenishment_contracts.sql)** — automatic municipal replenishment. `create_replenishment_contracts_for_due_stockpiles(p_limit)` is one set-based `INSERT ... SELECT ... ON CONFLICT (stockpile_id) ... DO NOTHING` over stockpiles whose `next_reorder_at` has already passed (same partial index Phase 3 built for its own due sweep), joined only to `provider_type = 'city'` providers -- the federal provider is structurally excluded from automation, matching the plan's "keep it a static placeholder" instruction. Pricing (`_government_item_base_price`) is a small hand-mirrored copy of `shared/economy.ts`'s `NPC_PRICE_CEILINGS` for the 9 fixed raw-resource keys -- plpgsql can't import the TS module, same "kept in sync by hand" tradeoff `shared/cities/stockpiles.ts` already documents for its own SQL mirror. `materialize_and_replenish_city_stockpiles_due()` composes this with Phase 3's `materialize_city_stockpiles_due()` into tick-city-stockpiles' single RPC call (materialize first so `quantity_requested` reflects current depletion, then create contracts for whatever's still due). `run_government_daily_update()` (another evolutionary `create or replace`, same pattern as 112→115) gets one more call to the same creation function after its own full stockpile sweep, since that's the point where municipal-consumption-index changes can newly push stockpiles below their reorder point between due-sweep cycles.
- **[`119`](../supabase/migrations/20260819230000_119_government_contract_award_and_delivery.sql)** — the two player-facing RPCs. `award_government_contract_atomic` (authenticated-granted, checks `auth.uid() = p_player_id` itself, same shape as `accept_contract_atomic`) lets a player claim an `available` contract with a business in any city -- the destination-city constraint is enforced at delivery, not award, since a player may need to move goods there first via the existing `execute_inventory_transfer` shipping path (no new freight system this phase; that's Phase 5/the trucking reach goal). `deliver_government_contract_atomic` (service_role-only, called via `createSupabaseServiceRoleClient()` like `fulfill_contract_atomic`) mirrors that function's *current* definition closely, including migration 108's journal-posting addition (a balanced `post_business_journal_entry` call, not just the legacy `business_financial_events` rows) so government contract revenue shows up correctly in the balance sheet/cash-flow statement/reconciliation -- consumes qualifying (`quality >= minimum_quality`) inventory via `compute_inventory_cost_relief`, rejects cleanly with `{ok:false, reason:'wrong_city'}` before mutating anything if the awarded business isn't located in the contract's destination city, then replenishes `city_stockpiles` by calling the existing `_materialize_city_stockpile_ids` helper twice (once to bring the checkpoint current, once more after adding the delivered quantity to recompute `next_reorder_at` against the new stock level) rather than duplicating that formula a third time.

**New domain surface** (`src/domains/government`, `DOMAIN.md` updated -- notes its first-ever dependency on `_shared/ownership` for award/deliver's business-ownership checks): `getGovernmentContractProviders()`, `getGovernmentContracts()` (filterable, bounded), `getGovernmentContractById()`, `awardGovernmentContract()`, `deliverGovernmentContract()`. New endpoints: `GET /api/government/contract-providers`, `GET /api/government/contracts`, `POST /api/government/contracts/[id]/award`, `POST /api/government/contracts/[id]/deliver`.

**A real, previously-unverified Phase 3 bug found and fixed**: migration 114's seed data and its `_materialize_city_stockpile_ids()` both called `make_interval(hours => (...)::double precision)` to compute `next_reorder_at` -- `make_interval`'s `hours` parameter is `integer`, not `double precision`, so Postgres has no matching overload and this fails outright with `42883` (function does not exist) the moment it's actually executed. Every session since Phase 1 had shipped this migration by hand-review only (Docker unavailable each time, per `AGENTS.md`'s open thread); this is the first session where Docker was actually running, and a clean `npx supabase db reset` failed on statement 6 of migration 114 immediately. Fixed both call sites in place (migration 114 was never pushed anywhere, so editing it directly is correct, not a patch migration) by replacing `make_interval(hours => x::double precision)` with `x * interval '1 hour'`, which Postgres supports natively for any numeric operand. **This means Phase 3 was non-functional from the moment it was written until today** -- `city_stockpiles` would have seeded successfully (that half doesn't hit the buggy branch when `base_consumption_per_hour = 0`... actually it does whenever any city has nonzero consumption, i.e. always) but the seed's `next_reorder_at` computation and every materialize call would have thrown, meaning `tick-city-stockpiles` and `run_government_daily_update()` would have errored on every single run had they ever been pushed to hosted. They were not (confirmed via `npx supabase migration list` reasoning in prior sessions' notes) so no live damage occurred, but this closes out `AGENTS.md`'s standing "three sessions in a row have shipped unexercised plpgsql" warning with a concrete example of exactly the kind of bug that warning was about.

**Verified against a real local Postgres instance for the first time** (Docker Desktop was running this session): clean `npx supabase db reset` now applies all 119 migrations end to end with no errors. Added [`test/finance/government-contract-delivery.test.ts`](../test/finance/government-contract-delivery.test.ts) (7 new integration tests, real RPC round trips against local Postgres/PostgREST, not mocks) covering the plan's own explicitly-requested cases: replenishment contract creation + idempotency (a second sweep call creates zero duplicates), city-vs-federal provider behavior (no contract ever references the federal provider), award/deliver happy path (payout, inventory relief, balanced journal, stockpile replenished, `next_reorder_at` pushed back into the future), rejecting award to a business the player doesn't own, rejecting delivery against an already-fulfilled contract, and rejecting delivery when the awarded business isn't in the contract's destination city (with a same-transaction assertion that nothing mutated on that rejection path). Each test creates its own fresh `city_stockpiles` row with a unique synthetic `item_key` rather than mutating one of the 90 real seeded rows, specifically so the suite is safe to rerun against the same local database without a reset in between (an earlier draft that reused `.limit(1)` on the shared seeded rows was nondeterministic across describe blocks and broke on a second run without a reset -- caught by actually running it twice before finalizing). Also manually verified `run_government_daily_update()` is idempotent within one economic day (`skipped: true` on the second call) and that `materialize_and_replenish_city_stockpiles_due()` (the new `tick-city-stockpiles` RPC) runs cleanly. Full `npm run typecheck`, `npm run typecheck:edge`, `npm run build`, `npm run test:finance` (63 passed, up from 56), and `npm run test:db-security` (12 passed -- confirms `award_government_contract_atomic` is authenticated-executable and every new service_role-only function, including the pre-existing but previously-unlisted `fulfill_contract_atomic`, is unreachable by anon/authenticated) all pass clean from a fresh `db reset`.

**Deliberately out of scope for this pass**: no City Page UI (the plan's proposed Available/My/Closed Contracts tabs -- same "architecture ready, UI later" pattern every prior CityPlan phase has followed), no route-based freight (Phase 5, cross-city delivery still depends on the existing abstract shipping/inventory-transfer path), no player-owned trucking (the reach goal).

## 2026-08-19 — CityPlan Phase 3: municipal stockpiles with lazy elapsed-time depletion

Per [`Documents/Plans/CityPlan.md`](Plans/CityPlan.md) ("Phase 3 - Municipal Stockpiles"), following Phase 2's dynamic world/city state. Three migrations:

- **[`114`](../supabase/migrations/20260819180000_114_city_stockpiles.sql)** — new `city_stockpiles` (`city_id`/`item_key` unique, `stored_quantity`/`target_quantity`/`reorder_point`/`critical_point`/`base_consumption_per_hour`/`minimum_quality`/`last_materialized_at`/`next_reorder_at`/`is_active`), indexed on `next_reorder_at` (partial, active-and-scheduled-only) so the due sweep never full-table-scans. Seeded 90 rows (the same 9 raw-resource keys Phase 1 already established × 10 cities) representing each city's own physical reserve, not NPC retail demand -- deliberately the same item taxonomy rather than inventing a new one. Per-capita hourly draw rates are uniform across cities and scaled by `population_baseline`; target is a 30-day (720h) reserve, reorder at 40%, critical at 15%, seeded full. Also adds the materialization math itself: `_materialize_city_stockpile_ids(uuid[])` (private, `service_role`-only) implements the plan's exact formula (`rate = baseConsumptionPerHour × populationScale × city.municipalConsumptionIndex × world.municipalConsumptionIndex × activeItemEventMultiplier`, `currentStock = max(0, storedQuantity − elapsedHours × rate)`) and the three-branch `next_reorder_at` recompute, in one atomic `UPDATE ... FROM` (no separate `FOR UPDATE` read phase needed -- the `UPDATE` itself locks its target rows, same reasoning as migration 112's per-city update). `activeItemEventMultiplier` compounds any active `city_events` modifier keyed `stockpile_<item_key>` (new convention, mirrors Phase 2's index-name keys) -- dormant until an event actually sets one, same "architecture ready, no live content yet" shape as Phase 2's event system. ## 2026-08-15 — Fixed stale-UI-until-refresh bug (sell/transfer actions not visually updating), dependency bump

**User-reported bug:** selling items and transferring items (and other business-page actions) didn't visually update until a hard page refresh. Root cause was **not** a missing resync call in the main sell/transfer paths — `MarketClient.tsx`, `InventoryClient.tsx`'s transfer flow, and the underlying domain services/routes were all already correct. The actual bug was a **race condition** in how fetched data gets written into the Zustand store:

- Every slice setter (`setBanking`, `setInventory`, `setMarket`, etc. in `game-store.ts`) is a blind overwrite with no ordering check.
- Two independent code paths fetch and write the same slice for the same mutation: the component's own `syncMutationViews(...)` resync (fired right after the mutation's API call resolves), and the realtime provider's postgres_changes-triggered refetch of the same table (fired independently off the DB commit notification). Nothing coordinated the two, so whichever HTTP response happened to land last won — regardless of which one was actually fresher. A manual refresh "fixed" it because it's a single clean load with no competing in-flight request.
- **Fix:** added `src/stores/slice-fetch-guard.ts` — a per-slice-key generation counter (`beginSliceFetch`/`isLatestSliceFetch`/`runGuardedSliceFetch`) shared between `src/stores/mutation-sync.ts` and `src/providers/realtime-provider.tsx`. Every slice fetch (businesses/banking/inventory/market/employees/contracts/production/`businessDetail:<id>`) now only commits its result if no newer fetch for that same key has been issued since. Both files were updated to route all their slice writes through this guard.

**Related fixes found in the same audit, all following the existing optimistic-update + `syncMutationViews` pattern:**
- `BankingClient.tsx` had five independent `*Submitting` flags gating five separate transfer/loan forms, so two forms could be submitted back-to-back and race each other's `banking` slice resync (on top of the guard fix above, this made Banking the easiest place to reproduce the bug — it's literally what the user called out). Collapsed all five buttons to share the existing `allBusy` flag.
- `EmployeesClient.tsx`'s roster row actions (`reactivate`, `unassign`, `fire`) had no in-flight guard at all, unlike `submitHire`/`submitAssign` in the same file. Added a shared `pendingRosterAction` lock across all three.
- `BusinessDetailsClient.tsx`'s three manufacturing-line actions (`unassignManufacturingWorker`, `setManufacturingLineRunning`, `retoolManufacturingLine`) patched the local business-detail entry but never called `syncMutationViews`, leaving the `employees` slice and the standalone `/production` page stale until an unrelated resync happened. Added the missing calls, matching `assignEmployeeToManufacturing` in the same file.
- `ProductionClient.tsx`'s `setRecipe`/`setRunning` used a raw `fetch()` instead of the `apiPatch`/`apiPost` wrappers and never called `syncMutationViews`, so a business's Operations tab (viewed via Businesses/`BusinessDetailsClient`) didn't reflect changes made from the Production page. This silently truncated the subtick window so `subTickIndex` only ever reached ~9 of the intended 0–19 range before resetting — roughly half the intended NPC shopper volume never ran. Fixed by changing the constant to `60`.
- **Item 5** — `tick-npc-purchases/index.ts`: the per-store loop had no error boundary, so one store throwing (e.g. an orphaned inventory row) zeroed out NPC traffic for every store after it in that pass. Wrapped the loop body in `try/catch` so a single store's failure is logged and skipped instead of aborting the run.
- **Item 6** — NavBarFix (`a9d6eec`) made business selection render `BusinessDetailsClient` in place on `/businesses` without changing the URL, but `realtime-provider.tsx` only activated business-detail realtime subscriptions when `pathname.startsWith("/businesses/")`, so finance/inventory/employee updates for the panel a player was actively viewing stopped subscribing. Fixed by also gating on whether the store's `businessDetails` slice has an active entry (`trackedBusinessDetailIds.length > 0`) while on `/businesses`, and having `BusinessesClient.handleBackToList` call `removeBusinessDetail(...)` so that signal stays accurate.
- **Item 7** — `settleEmployeeWages` posted the wage debit, then made two more separate network calls; if either failed, the debit had posted but `unpaid_wage_due` never cleared, so a retry could re-charge the same wage. New RPC `settle_employee_wages_atomic` (migration [`074`](../supabase/migrations/20260815020000_074_settle_employee_wages_atomic.sql)) makes the debit + debt-clear atomic, modeled on `assign_employee_atomic`'s locking. The restore-to-open-spot step is now a best-effort follow-up in application code with no financial side effect riding on it.

**Medium fixes:**
- **Item 8** — NPC sale settlement (`settleStoreInventorySale`) did an unlocked read-then-write against `business_inventory`/`store_shelf_items`, unlike the player-facing purchase RPC. Ported into a new locked RPC, `settle_store_inventory_sale_atomic` (migration [`075`](../supabase/migrations/20260815030000_075_settle_store_inventory_sale_atomic.sql)), mirroring `execute_market_purchase`'s `FOR UPDATE` pattern; the edge function now calls it instead of touching those tables directly.
- **Item 9** — `/api/realtime-auth` returned the raw session JWT without verifying it first. Now calls `verifyCustomJwt` and returns 401 on an invalid/expired token before handing it back.
- **Item 10** — Resolved as a side effect of item 7 (the dangerous "unhandled exception after the debit already posted" path no longer exists).
- **Item 11** — `pay_loan_from_checking` checked the checking balance against the raw requested amount before clamping to what was actually owed, so "pay off the rest of my loan" could be wrongly rejected. Migration [`076`](../supabase/migrations/20260815040000_076_fix_loan_overpayment_clamp_order.sql) reorders the clamp before the balance check.
- **Item 12** — `BusinessesClient.handleSelectBusiness` had no stale-response guard; a slow fetch for one business could overwrite a faster one for another. Added a request-token ref that discards stale resolutions.
- **Item 13** — `buyMarketListing`'s weighted-average cost-basis update on the buyer's inventory row happened in a second, separately-locked round trip after `execute_market_purchase` returned, so concurrent purchases could clobber each other's cost basis. Migration [`079`](../supabase/migrations/20260815070000_079_execute_market_purchase_cost_basis.sql) computes it inside the RPC's existing lock on that row instead; the redundant JS-side read/update was removed.

**Low fixes:**
- **Item 14** — `fire_employee_atomic` deleted an employee unconditionally, silently erasing any `unpaid_wage_due`. Migration [`077`](../supabase/migrations/20260815050000_077_fire_employee_unpaid_wage_guard.sql) blocks firing until wages are settled.
- **Item 15** — `append_business_financial_event` was left grantable to `authenticated` when its siblings were hardened in `072`. Migration [`078`](../supabase/migrations/20260815060000_078_restrict_business_financial_event_to_service_role.sql) restricts it to `service_role`; `insertBusinessFinancialEvents` now calls it via the service-role client.

The orphaned `/businesses/[id]/page.tsx` route is a consequence of NavBarFix's intentional in-place rendering, not a bug in itself; the route still works fine when hit directly, and item 6 already fixes the actual regression (realtime updates). Re-adding URL navigation would fight that UX choice and wasn't requested.

## 2026-08-15 — Supabase environment setup, critical security hardening, docs consolidation

**Security fixes (migration [`072_critical_security_hardening.sql`](../supabase/migrations/20260815000000_072_critical_security_hardening.sql)):**
A security review (see [`Bugs.md`](Bugs.md)) found three critical, directly-exploitable issues:
1. `append_personal_transaction` / `append_business_account_entry` were granted `EXECUTE` to `authenticated` with no restriction on `transaction_type`/`category` — any player could call them directly via PostgREST with their own JWT and credit themselves arbitrary funds. Fixed by revoking `authenticated` access and restricting to `service_role`; the app now calls them through a dedicated service-role client (`src/lib/supabase-service-role.ts`).
2. The `players` RLS update policy allowed a player to PATCH their own `role` column to `admin`. Fixed with a `BEFORE UPDATE` trigger (`prevent_player_role_self_escalation`) that reverts any `role` change not made by `service_role`.
3. Double-spend race in `transfer_between_own_accounts`, `transfer_between_personal_and_business`, `transfer_between_own_businesses`, and `pay_loan_from_checking` — balance was read, then debited in a separate statement with no lock. Fixed by adding `SELECT ... FOR UPDATE` on the account/business/loan rows (in a stable lock order to avoid deadlocks) before the balance check.
