## 2026-08-19 — CityPlan Phase 1: static city profiles, resource abundance, and a seeded route matrix

Per [`Documents/Plans/CityPlan.md`](Plans/CityPlan.md) ("Phase 1 - City Profiles, Resources and Routes"), the first phase of the proposed regional-economy layer (Phases 2-7 and the trucking reach goal remain unbuilt). Migration [`111`](../supabase/migrations/20260819150000_111_city_profiles_resources_routes.sql):

- **Extended `cities`** with `population_baseline`, `business_tax_rate`, `property_cost_index`, `utility_cost_index`, `base_labor_index`, `latitude`/`longitude`, and `is_active`, backfilled with real-world-approximate values for the existing 10 cities.
- **New `city_resource_modifiers`** table (`city_id`, `resource_key`, `abundance_multiplier` 0-2, unique per city/resource): seeded 90 rows (9 raw-resource keys × 10 cities — `water`, `iron_ore`, `coal`, `copper_ore`, `raw_wood`, `crude_oil`, `wheat`, `potato`, `red_grape`), thematically weighted per city (e.g. Houston crude_oil 2.0x, Phoenix copper_ore 2.0x, Philadelphia coal 1.6x, some cities intentionally at 0x to force trade, per the plan's design principle). No row for a given city/resource pair defaults to neutral (1.0x) at read time, not by inserting redundant rows.
- **New `city_routes`** table (`from_city_id`, `to_city_id`, `road_distance_miles`, `baseline_drive_minutes`, `base_freight_cost_per_lb_mile`, `toll_cost`): seeded a curated, symmetric 90-row matrix (all 45 unique city pairs, both directions) with approximate real-world driving distances and a 55mph baseline pace. **Not yet wired into travel/shipping** — `TravelClient`/`calculateTravelQuote`/`calculateShippingQuote` (`src/domains/cities-travel/topology.ts`) still use the pre-existing region-tier system; `city_routes` is reference data only until CityPlan Phase 5 (route-based freight) replaces that tier system.
- Both new tables follow `cities`' existing RLS pattern exactly: RLS enabled, a single `select`-for-`authenticated` policy, no write policy — they change only via migration (base grants come from migration 097's `ALTER DEFAULT PRIVILEGES`, scoped to objects `postgres` creates, so no separate grant statement was needed).

**Wired into gameplay, not just schema:** resource abundance was explicitly specified in Phase 1 as `cityAdjustedBaseOutput = baseExtractionOutput * cityResourceAbundance` (quantity only, never quality — a repeated design principle in the plan). Added `shared/cities/resources.ts` (`applyCityResourceAbundance`, clamped 0-2) and its edge-function wrapper `supabase/functions/_shared/city-resources.ts` (`getCityResourceAbundanceMap`, batched once per tick per touched city — same pattern as the existing per-tick upgrade-effects batching, not a per-slot query). [`tick-extraction`](../supabase/functions/tick-extraction/index.ts) now multiplies each slot's output by its business's city + output-item abundance before rounding to produced units. This affects all five extraction business types (`mine`, `farm`, `water_company`, `logging_camp`, `oil_well`) through the one shared code path, including farm crop yield.

**Domain layer:** `src/domains/cities-travel` (owns `cities`, `city_resource_modifiers`, `city_routes`, `travel_log`, `shipping_queue`) gained `getCityResourceModifiers()`, `getCityRoutes()`, `getRouteBetweenCities()`, each with the same 5-minute warm-instance cache as the existing `getCities()` (static reference data, safe to cache across requests). New read-only endpoints `GET /api/cities/resources` and `GET /api/cities/routes`.

**Deliberately out of scope for this pass** (left for later CityPlan phases per the plan's own phase breakdown): no dynamic `city_economic_state`/`world_economic_state`, no municipal stockpiles or government contracts, no Federal provider placeholder, and no City Page UI (the plan's proposed Overview/Resources/Business Environment/Municipal Stock/Contracts/Logistics tabs) — most of those tabs depend on schema that doesn't exist yet (stockpiles, contracts). The existing Travel page was not changed.

Verified with a clean `npm run typecheck` and `npm run typecheck:edge` (now covers the new `_shared/city-resources.ts` import in `tick-extraction`). **Not verified against a live database or `npm run build`** — Docker Desktop wasn't running in this session, so a local `supabase db reset` (which would exercise the migration end-to-end, including the multi-row `VALUES`/`UNION ALL`/`ON CONFLICT` seeding) could not be performed; the SQL was reviewed by hand instead (row counts double-checked: 45 unique city pairs × 2 directions = 90 routes, 9 resource keys × 10 cities = 90 modifiers). **Not yet pushed to hosted** — needs `npx supabase db push` plus `npx supabase functions deploy tick-extraction`, and a local `supabase db reset` smoke test is recommended before that push given the unverified migration.

## 2026-08-19 — AccountingFixPlan Phase H (final phase): reconciliation, historical backfill, finance UI, and a real production-retool bug found in the final audit

Per [`Documents/Plans/AccountingFixPlan`](Plans/AccountingFixPlan) — the last phase of the finance/accounting repair project (Phases A–G already shipped: tests/Chart of Accounts/journal, payroll, inventory cost-basis, manufacturing/extraction, storefront/market/contracts/B2B, shipping/upgrades, and the real financial statements). Full detail (including the balance-sheet arithmetic worked out by hand) is in the plan file's own "Phase H notes" section; this entry is the short version.

**Reconciliation** (item 53): migration [`109`](../supabase/migrations/20260819130000_109_reconciliation_and_backfill.sql) adds `reconcile_business_accounting(p_business_id)`, a read-only SQL function reporting cash ledger vs stored `cash_balance`, journal debits vs credits, and inventory book value — it never repairs anything, only reports. [`src/domains/businesses/reconciliation.ts`](../src/domains/businesses/reconciliation.ts) combines that with the existing `getBalanceSheet`/`getCashFlowStatement` for the full report (Assets=Liabilities+Equity, beginning+netCF=ending cash), for one business or every business, exposed at `GET /api/admin/finance/reconciliation`.

**Historical backfill** (item 58): the same migration adds two idempotent functions — `backfill_reconstruct_inventory_cost_basis()` (repairs `business_inventory` rows left with `total_cost IS NULL` by pre-Phase-C bugs) and `backfill_capitalize_historical_upgrades()` (writes the `fixed_assets` financial event for upgrade purchases made before Phase F's atomic RPC existed, reconstructed from `business_upgrade_projects.quoted_cost` + timestamp). Both run once at migration time (a no-op on a clean database) and stay callable for later use against hosted.

**Finance UI** (item 59): `getBusinessFinanceDashboard` ([`src/domains/businesses/finance.ts`](../src/domains/businesses/finance.ts)) now returns an all-time `cashFlowStatement` and a `reconciliation` report, and fixes a real bug Phase G's own notes had flagged and deferred: the per-period "Owner Equity"/valuation KPI was hardcoding liabilities to 0 instead of using the real Wages Payable balance. [`BusinessFinanceDashboard.tsx`](../src/components/businesses/BusinessFinanceDashboard.tsx) gained a Cash Flow Statement panel and a Reconciliation panel (pass/fail checks) using the page's existing table component.

**Final audit found a real, pre-existing bug** (item 60): production line retooling (`retoolExtractionSlot`/`retoolManufacturingLine`, [`src/domains/production/service.ts`](../src/domains/production/service.ts)) charged its cost with zero `business_financial_events` coverage and as three separate unlocked round trips — and, worse, `extraction_slots`' status `CHECK` constraint was never widened to allow `'retooling'` when per-line retooling shipped (migration `053` only added columns, not the status value), so `retoolExtractionSlot` has apparently never worked: it would debit a player's cash and then fail on the status update. Migration [`110`](../supabase/migrations/20260819140000_110_production_retool_atomicity.sql) fixes the constraint and adds two atomic RPCs (`retool_extraction_slot_atomic`, `retool_manufacturing_line_atomic`) that charge the cost, post a balanced journal entry + financial event, and apply the retool in one transaction.

Verified with a clean `npx supabase db reset`, `npm run typecheck`, `npm run typecheck:edge`, `npm run build`, and `npm run test:finance` (56 passed, up from 48, 0 regressions). Interactive browser verification of the new UI panels was **not** performed — the only reachable dev server was already running against the hosted project (pointed there via `.env.local`, which lacked migrations 109/110 at the time) and this session correctly declined to kill another session's process; Next.js 16 also blocks a second `next dev` instance in the same project directory even on a different port.

**Update, same day:** pushed to hosted (`npx supabase db push` — all AccountingFixPlan migrations 096–110 now match on remote) and redeployed the three edge functions this project ever touched (`tick-wages`, `tick-extraction`, `tick-manufacturing`); `tick_run_logs` confirms all three running clean post-deploy. Verified live: the `extraction_slots` retool-status bug fix is in effect on hosted, and the two backfill functions found zero rows needing repair in hosted's actual data (0 null-cost inventory rows, 0 uncapitalized historical upgrade projects).

## 2026-08-19 — AccountingFixPlan Phase C: shared inventory cost-basis relief/addition helpers

Per [`Documents/Plans/AccountingFixPlan`](Plans/AccountingFixPlan) (Phase C of the finance/accounting repair, following Phase A — test suite/Chart of Accounts/journal, see below — and Phase B/payroll). The weighted-average inventory cost RELIEF formula (shrink `total_cost` proportionally when quantity drops) was duplicated inline across 9 PL/pgSQL functions, and the ADDITION formula (blend an incoming unit cost into `total_cost` when quantity grows) across 4 more — each picked up separately as prior migrations patched individual accounting bugs one RPC at a time. Migration [`099`](../supabase/migrations/20260819030000_099_shared_inventory_cost_basis_helpers.sql) adds two pure-SQL helpers, `compute_inventory_cost_relief` and `compute_inventory_cost_addition` (the latter mirroring the pre-existing TS-side `computeWeightedAverageCost()`), and rewires every one of those 13 call sites — `execute_market_purchase`, `execute_inventory_transfer`, `settle_store_inventory_sale_atomic` + its batch variant, `settle_market_listing_npc_sale_atomic`, `add_business_inventory_quantity`, and all of `_settle_buy_order_fill`/`place_market_buy_order`/`sweep_buy_orders_for_new_listing`/`fulfill_market_buy_order` — to call the shared helper instead of reimplementing the math. All signatures are unchanged (`create or replace function`, ACLs preserved automatically).

**Real bug fixed, not just a refactor:** two of the three duplicated relief variants (`execute_inventory_transfer` and the buy-order functions) left a row's `total_cost` as `NULL` forever once relieved, if the row had no `total_cost` to begin with — and `SUM(business_inventory.total_cost)` silently skips nulls, so that row's real quantity contributed $0 to the Balance Sheet's inventory asset. The canonical helper always reconstructs `total_cost` from `unit_cost × remaining_quantity` in that case, matching the one variant that already did this correctly (storefront/NPC sale sites). Also closed a smaller divergent-math risk: `execute_inventory_transfer` now returns `sourceUnitCost`/`sourceRelievedCost` in its jsonb result, and [`src/domains/inventory/service.ts`](../src/domains/inventory/service.ts)'s `transferItems()` uses those directly for the B2B transfer's COGS financial event instead of a second, separately-locked pre-read plus its own JS float division (which could diverge by a cent from what the RPC actually relieved).

Deliberately out of scope for this phase (per the plan's own breakdown): `tick-manufacturing`/`tick-extraction` still do zero cost relief on consumed raw materials (Phase D); B2B transfer's destination-side cost-basis write stays in TS, not yet folded into the RPC (Phase E, full B2B atomicity).

Verified with a clean `npx supabase db reset`, `npm run test:finance` (33 passed, 3 expected-fail — unchanged from Phase B), `npm run typecheck`, `npm run typecheck:edge`, and a manual spot-check of both helper functions directly against Postgres (including the plan's own worked example: 100 units @ $1,000 total_cost, relieve 25 → $250 relieved, 75 units / $750 remaining). **Not yet pushed to the hosted project** — needs `npx supabase db push`.

## 2026-08-19 — Fixed `employee_skills_level_check` violation (23514) in tick-manufacturing/tick-extraction

User-reported hosted error (`new row for relation "employee_skills" violates check constraint "employee_skills_level_check"`, 2026-08-19 10:44). Root cause: both [`supabase/functions/tick-manufacturing/index.ts`](../supabase/functions/tick-manufacturing/index.ts) and [`supabase/functions/tick-extraction/index.ts`](../supabase/functions/tick-extraction/index.ts) award skill XP every production tick with a `while (nextXp >= XP_PER_LEVEL) { nextLevel += 1; }` level-up loop that had no upper bound, while `employee_skills.level` is schema-capped at 100 (migration `016`). Any employee who accumulated enough XP to level past 100 made every subsequent skill-XP `UPDATE` on that row fail. No data corruption resulted — the failing writes were rejected/rolled back, so affected rows stayed at whatever valid level they were already at — but that same employee's production tick has been throwing (and presumably failing the tick for that job/slot) since they capped out.

Fix: both loops now stop once `nextLevel` reaches 100 (`while (nextXp >= XP_PER_LEVEL && nextLevel < 100)`), so xp still accrues but level stays valid. No migration/backfill needed. Verified with a clean `npm run typecheck:edge`, then deployed both functions to the hosted project (`npx supabase functions deploy tick-manufacturing` / `tick-extraction`).

"operating_expense"` fallback — now explicit, not a change.

**Unplanned infra fix, needed to unblock Phase A's own tests** (migration [`097`](../supabase/migrations/20260819000001_097_baseline_schema_grants.sql)): discovered that a from-scratch local `supabase db reset` leaves `anon`/`authenticated`/`service_role` with **zero** base table privileges — not even `SELECT` on RLS-less reference tables like `cities` (`permission denied for table cities` via PostgREST, confirmed with a bare `curl` using the anon key). Migration 097 restores the baseline grants (`GRANT ... ON ALL TABLES IN SCHEMA public` plus `ALTER DEFAULT PRIVILEGES` so future migrations' tables inherit it automatically) — additive and safe; RLS policies still gate row access on every table that has RLS enabled, this only restores the base grant RLS itself depends on. **Not yet pushed to the hosted project** — needs `npx supabase db push` before this is fixed there too (though hosted likely isn't actually broken, since its control plane grants this separately from migration history; this is primarily a local/CI parity fix).

Verified with a clean `npm run typecheck`, `npm run typecheck:edge`, and `npm run test:finance` (33 passed, 4 expected-fail).

**Still open:** migration 097 needs pushing to the hosted project. Phase A intentionally left the actual accounting bugs (payroll accrual, freight capitalization, upgrade capitalization, extraction cost basis) unfixed — that's Phases B–D/F. ## 2026-08-18 — Business upgrades switched from compounding percentages to flat realistic units

Per-instruction rework of every non-quality business upgrade (`multiplier`, `reduction_multiplier`, `traffic_multiplier`, `conversion_multiplier`, `price_tolerance` — 69 of the ~105 definitions in [`src/config/business-upgrades.ts`](../src/config/business-upgrades.ts); quality (`flat_quality`) and slot upgrades (`flat_slots`) were left untouched since they were already unit-based, not percentage). Previously each level multiplied `baseEffect` by `gainMultiplier^(level-1)` — a small, slow-compounding percentage (e.g. Extraction Efficiency: +8%, +8.4%, +8.8%, …). Now each level adds a flat, sized-for-realism unit straight to the base (e.g. Extraction Efficiency: baseEffect 0.5 → level 1 is a flat +50%, level 2 +100%, …), mirroring how Quality and Worker/Listing Slots already worked. `baseCost`/`costMultiplier` were rescaled per upgrade (roughly cost ∝ power delivered, plus a "very expensive" surcharge on infinite/finite upgrades) so the bigger jumps aren't free — specialization (one-shot, `maxLevel: 1`) capstones were scaled by power ratio alone since they were already priced at the top of the tree. The 6 `reduction_multiplier` upgrades (Water Efficiency, Compost System, Waste Boiler, Forge Lining, Cold Storage, Dust Collector) were converted from `isInfinite: true` to finite `maxLevel: 6` @ 15%/level, landing exactly on the existing 90% (`0.1` floor) reduction cap at the final level instead of asymptotically approaching it forever.

Engine changes: [`shared/upgrades/effects.ts`](../shared/upgrades/effects.ts) `resolveUpgradeEffectValue` now computes `1 + baseEffect × level` (linear) instead of `baseEffect × gainMultiplier^(level-1)` (compounding), and reduction upgrades cap at `definition.maxLevel`. [`shared/upgrades/runtime.ts`](../shared/upgrades/runtime.ts)'s `resolveMultiplier`/`resolveReductionMultiplier` helpers were updated the same way (signature changed: no more `gainMultiplier` param; reduction now takes `maxLevel`). UI: `ui_format` values `percent_up`/`percent_down` renamed to `unit_up`/`unit_down`; [`src/domains/upgrades/formatting.ts`](../src/domains/upgrades/formatting.ts) now renders the raw unit delta (`+0.50`) instead of a percentage (`+50%`).

**Found along the way, deliberately left alone (explicit instruction):** the production ticks (`tick-extraction`, `tick-manufacturing`, `tick-npc-purchases`) don't read `src/config/business-upgrades.ts` at all — they call a hand-duplicated resolver in [`supabase/functions/_shared/business-upgrades.ts`](../supabase/functions/_shared/business-upgrades.ts) that only implements the 11 shared upgrade keys (Extraction Efficiency, Worker Capacity, Tool Durability, Ore Quality, Water Efficiency, Production Efficiency, Equipment Quality, Storefront Appeal, Listing Capacity, Customer Service, and implicitly Crop Yield). Every business-specific upgrade (Blasting Permits, Combine Harvester, Robotic Welder, all ~58 others) currently affects the UI preview only, not real production — this predates this change (the edge copy's numbers had already drifted from config, e.g. hardcoded `1.12`/`1.05` for Extraction Efficiency vs config's old `1.08`/`1.05`). Fixed the drift for the 11 keys that *do* run in production by having the edge copy import `BUSINESS_UPGRADE_DEFINITIONS` from config directly instead of hardcoding numbers (so it now reflects the new unit-based values), but did not wire up the other ~58 dead upgrade keys — that's a separate, larger job. Doing so required adding explicit `.ts` extensions to two previously-unresolved relative imports (`src/config/business-upgrades.ts` → `./businesses.ts`, `src/config/businesses.ts` → `../../shared/businesses/store.ts` and `./business-upgrades.ts`) since `src/config/businesses.ts` had never been pulled into the Deno type-check graph before.

## 2026-08-17 — Worked through Documents/SBAudit.md (Supabase performance audit): all 3 Critical, all 8 High, most Medium/Low findings

Full pass over the Supabase performance audit ([`SBAudit.md`](SBAudit.md)), migrations [`089`](../supabase/migrations/20260817000000_089_maintained_account_balances.sql)–[`095`](../supabase/migrations/20260817060000_095_tick_travel_cadence.sql). Pre-launch, so changes were pushed straight to the hosted project (`npx supabase db push` + `functions deploy`) rather than staged — no live players yet, per direct instruction. Every migration and edge-function deploy in this pass was verified against a clean `npm run typecheck` / `npm run build` / `npm run typecheck:edge`, and each tick deploy was confirmed running with `status: "ok"` in `tick_run_logs` afterward.

**Critical:**
- **C1** — `get_online_player_previews` summed every player's *entire* ledger history every 60s per open tab, for every player in the DB, before joining down to who's online. Migration 089 adds maintained `bank_accounts.balance` / `businesses.cash_balance` columns, kept in sync by `AFTER INSERT` triggers on the (append-only) `transactions` / `business_accounts` ledgers, and rewrites `get_bank_account_balance`, `get_business_account_balance`, `get_player_account_balances`, and `get_online_player_previews` to read/aggregate those columns instead of summing history — the last one now also filters to the online player set *before* aggregating, not after. Backfill verified to match the live ledger sum exactly (spot-checked: 500.00 = 500.00). Same-signature swap, so no app code changed for the three getter RPCs. Existing lock ordering in the transfer/loan RPCs (migration 072) is untouched — they already lock the account row `FOR UPDATE` before reading balance, and the trigger's write lands on that same already-locked row.
- **C2** — `getResolvedBusinessUpgradeEffects` was called once per active extraction slot / manufacturing line / store instead of once per business per tick, each call re-deriving from scratch. Added `getResolvedBusinessUpgradeEffectsForBusinesses` (`supabase/functions/_shared/business-upgrades.ts`) that batches the upgrade/project lookups across every business touched in one tick invocation; `tick-extraction`, `tick-manufacturing`, and `tick-npc-purchases` now resolve effects once per unique business before their per-row loops instead of inside them.
- **C3** — The realtime provider's single `useEffect` mixed identity-scoped channels (player/chat/mail) with route-scoped ones, keyed partly on `pathname` — every in-app navigation tore down and reconnected *everything*, including a fresh `/api/realtime-auth` token fetch. Split `src/providers/realtime-provider.tsx` into three effects: an identity effect (`[hydrated, playerId]` only — owns the socket/token/player/chat/app-shell channels), a mail effect, and a route effect (owns everything gated by `activeRealtimeModules`). The route/mail effects share the identity effect's client instance via a stable `useState`-held client and an `identityReady` gate, and report their refresh functions back to the identity effect through refs so its fallback poll still covers all three without re-subscribing on navigation.

**High:**
- **H1** — A mutation's own resync and the realtime provider's postgres_changes-triggered refetch of the same slice each fired their own GET when they landed close together; the existing per-slice generation counter (`slice-fetch-guard.ts`) stopped the stale one from being *applied* but not from being *requested*. Added in-flight-fetch sharing to `runGuardedSliceFetch` — a second caller for the same slice key now awaits the first caller's request instead of firing another.
- **H2** — Folded into the C3 realtime-provider rewrite: per-business (`business-balances-*`) and per-account (`transactions-*`) channels are now one `business_id=in.(...)` / `account_id=in.(...)` channel each instead of one channel per business/account.
- **H3** — Also folded into C3: `mail-threads-*` / `mail-messages-*` were unfiltered (`event: "*"` on the full table, every player's mail activity pushed to every client). Now filtered to the current player's known thread ids (`id=in.(...)` / `thread_id=in.(...)`). A brand-new thread the player doesn't know about yet is still caught live via the already-filtered `mail_thread_participants` channel, which triggers a full mailbox refetch.
- **H4** — `tick-wages` pulled every employee ever hired (no status filter) every 15 minutes. Added `.neq("status", "fired")` (fired employees can never be charged again) plus a supporting partial index (migration 090, `idx_employees_active_created`).
- **H5** — Business-detail page loads re-verified ownership with a fresh `businesses` select for each of upgrades/upgrade-projects/finance-dashboard, on top of the one `getBusinessById` call `loadBusinessDetailsEntry` already made. Added `getBusinessUpgradesById`, `getBusinessUpgradeProjectsById` (`businesses/service.ts`) and re-exported finance.ts's business-object-accepting `getBusinessFinanceDashboard` as `getBusinessFinanceDashboardForBusiness` — all three skip the redundant check when the caller already holds a verified `Business` row. Also fixed the same pattern inside `purchaseUpgrade` (was re-verifying 3 times across one call). `getProductionStatus`/`getManufacturingStatus` still re-verify internally (`ensureOwnedBusinessType`) — left as-is; threading a pre-verified business through those touches a more widely-shared helper and felt like a separate, more invasive change.

## 2026-08-15 — Fixed stale-UI-until-refresh bug (sell/transfer actions not visually updating), dependency bump

**User-reported bug:** selling items and transferring items (and other business-page actions) didn't visually update until a hard page refresh. Root cause was **not** a missing resync call in the main sell/transfer paths — `MarketClient.tsx`, `InventoryClient.tsx`'s transfer flow, and the underlying domain services/routes were all already correct. The actual bug was a **race condition** in how fetched data gets written into the Zustand store:

- Every slice setter (`setBanking`, `setInventory`, `setMarket`, etc. in `game-store.ts`) is a blind overwrite with no ordering check.
- Two independent code paths fetch and write the same slice for the same mutation: the component's own `syncMutationViews(...)` resync (fired right after the mutation's API call resolves), and the realtime provider's postgres_changes-triggered refetch of the same table (fired independently off the DB commit notification). Nothing coordinated the two, so whichever HTTP response happened to land last won — regardless of which one was actually fresher. A manual refresh "fixed" it because it's a single clean load with no competing in-flight request.
- **Fix:** added `src/stores/slice-fetch-guard.ts` — a per-slice-key generation counter (`beginSliceFetch`/`isLatestSliceFetch`/`runGuardedSliceFetch`) shared between `src/stores/mutation-sync.ts` and `src/providers/realtime-provider.tsx`. Every slice fetch (businesses/banking/inventory/market/employees/contracts/production/`businessDetail:<id>`) now only commits its result if no newer fetch for that same key has been issued since. Both files were updated to route all their slice writes through this guard.

**Related fixes found in the same audit, all following the existing optimistic-update + `syncMutationViews` pattern:**
- `BankingClient.tsx` had five independent `*Submitting` flags gating five separate transfer/loan forms, so two forms could be submitted back-to-back and race each other's `banking` slice resync (on top of the guard fix above, this made Banking the easiest place to reproduce the bug — it's literally what the user called out). Collapsed all five buttons to share the existing `allBusy` flag.
- `EmployeesClient.tsx`'s roster row actions (`reactivate`, `unassign`, `fire`) had no in-flight guard at all, unlike `submitHire`/`submitAssign` in the same file. Added a shared `pendingRosterAction` lock across all three.
- `BusinessDetailsClient.tsx`'s three manufacturing-line actions (`unassignManufacturingWorker`, `setManufacturingLineRunning`, `retoolManufacturingLine`) patched the local business-detail entry but never called `syncMutationViews`, leaving the `employees` slice and the standalone `/production` page stale until an unrelated resync happened. Added the missing calls, matching `assignEmployeeToManufacturing` in the same file.
- `ProductionClient.tsx`'s `setRecipe`/`setRunning` used a raw `fetch()` instead of the `apiPatch`/`apiPost` wrappers and never called `syncMutationViews`, so a business's Operations tab (viewed via Businesses/`BusinessDetailsClient`) didn't reflect changes made from the Production page. Converted to the standard wrapper + resync pattern.

Verified with a clean `npm run typecheck` and `npm run build` after all changes.

**Dependency bump (same session):** updated `package.json` to Next 16.3.1, React/React DOM 19.2.8, TypeScript 6.0.2 (major bump from 5.9.2), `@supabase/ssr` 0.12.4, `@supabase/supabase-js` 2.112.3, `react-hook-form` 7.85.0, Zod 4.4.3, Zustand 5.0.15; Tailwind intentionally held at 3.4.18 (Tailwind 4 is a config migration, not attempted here). Verified via clean `node_modules`/`package-lock.json` reinstall, `npm run typecheck`, and `npm run build` — all passed.
